# Feature — Public API (#5) + MCP Server (#25)

Status: DESIGN. Owner: platform / agent-surface.
Depends on: `docs/roadmap/SCHEMA-V2.md` (soft — ships useful on v1, richer on v2).
This is the **AI-native differentiation**: neobankbeat already exposes `data.json`,
`openapi.json`, `llms.txt`, `.well-known/api-catalog` and an agent-skill. This feature
turns that flat surface into (a) a queryable **static REST API** and (b) an **MCP
server** so any agent can call `search_banks` / `compare_banks` / `similar_banks` /
`get_bank` without downloading and parsing the whole 368-entity blob.

---

## 1. Overview & user value

Today an agent that wants "self-custodial neobanks in Germany with Apple Pay" must
`GET /data.json`, hold all 368 records in context, and filter by hand. That is ~200 KB
of tokens per question and requires the agent to know the schema. Two consumers are
underserved:

1. **Programmatic consumers** (dashboards, notebooks, other sites) want small, cache-
   friendly, CORS-enabled JSON slices: "page 2 of banks", "all banks in France",
   "the slim card for Chime". They do not want to reimplement pagination client-side
   against a 200 KB file.
2. **Agents / LLMs** want *tools*, not files. An MCP server that answers
   `search_banks({country:"DE", features:["self_custody","apple_pay"]})` with a slim
   ranked list is worth an order of magnitude less context than the raw dump, and it is
   discoverable through the MCP ecosystem (Claude, Cursor, etc.).

Value: neobankbeat becomes the **default machine-readable source of neobank facts** —
the thing an agent reaches for the way it reaches for a weather API. Reinforces the
existing "agent-friendly parallel surface" (llms.txt, api-catalog, agent-skills) that
the site already leans on for SEO/GEO.

Both halves are **read-only, unauthenticated, MIT** — consistent with the current
posture (no key, no rate limit beyond CDN).

---

## 2. Hard constraint: static hosting, deterministic build

The site is pure static files on Vercel (pipeline audit §5). There is **no request-time
compute** and the reproducibility CI job re-runs the builders and fails on any `git
diff`. Consequences that shape the whole design:

- **No true server-side query params.** `/api/banks?country=DE&page=2` cannot be
  computed at request time without a serverless function. Serverless functions are
  nondeterministic relative to the committed build and would sit outside the
  reproducibility chain — **rejected**. Instead we **pre-generate every response as a
  committed static JSON file** and push arbitrary multi-facet querying into the client /
  MCP layer (which loads a slim index once and filters in memory).
- **Everything must be emitted by a committed builder and checked in.** The natural
  home is `tests/build-agents.mjs` (already the sole owner of `openapi.json`,
  `.well-known/api-catalog`, `.well-known/agent-skills/*`; imported by
  `build-pages.mjs`, which is in the reproducibility chain). We extend it, we do not add
  a new out-of-chain script.
- **Deterministic ordering.** Every list/shard is sorted by a stable key (name asc,
  ties broken by slug) so byte output never churns.

## 3. Static REST API — endpoint design

All endpoints live under `/api/` in the build output, served as `application/json` with
`Access-Control-Allow-Origin: *`. Generated by `build-agents.mjs` from `data.json`.

### 3.1 Slim vs full payload

- **Slim record** (used in every list/collection response) — the ~14 fields agents
  filter and rank on. Keeps list responses small and cache-hot:
  `{ id, name, slug, url, category, custody, regulation_type, region, hq, founded,
     card_networks, kyc, stablecoins, features_summary }`
  where `features_summary` is the array of `features.*` keys whose value is `true`
  (v2), or the `services[]` array as a fallback on v1. Prose/rate fields, investors,
  timeline, partners are **omitted** from slim.
- **Full record** — the complete entity object exactly as in `data.json` (all v1 + all
  v2 fields), served per-entity at `/api/banks/<slug>.json`.

Every slim record carries `url` = canonical `/n/<slug>/` and `api` =
`/api/banks/<slug>.json`, so a consumer can always hydrate slim → full in one hop.

### 3.2 Collection endpoints (pre-generated)

| Path | Contents |
|---|---|
| `/api/index.json` | API manifest: version, `generated` (from changelog), entity count, list of every endpoint + facet vocab. The one URL an agent needs to bootstrap. |
| `/api/banks.json` | **Slim** list of all 368, sorted, with `meta` (total, as_of, page size, page count). |
| `/api/banks/page/<n>.json` | Slim, paginated (e.g. 50/page → 8 pages). Each carries `meta.next`/`meta.prev` URLs. Deterministic paging over the sorted list. |
| `/api/banks/<slug>.json` | **Full** single entity. 368 files. |
| `/api/countries.json` / `/api/countries/<slug>.json` | Country facet index + per-country slim list. |
| `/api/cards.json` | Card-network / card-form / card-funding facets (from v2 `card_networks[]`,`card_form[]`,`card_funding[]`; falls back to v1 `card_network`). |
| `/api/stablecoins.json` | Banks with `stablecoins:true`, plus per-ticker breakdown from v2 `stablecoin_tickers[]`. |
| `/api/licenses.json` / `/api/licenses/<slug>.json` | `regulation_type` facet index + per-type slim list. |
| `/api/search-index.json` | Prebuilt slim search index (see §3.4). |

Facet shards are **single-dimension only** (by country, by category, by regulation, by
network, by feature). We deliberately do **not** pre-generate the combinatorial cross
product (country × feature × network) — that is what the client/MCP in-memory filter is
for. This bounds build output to a few hundred small files instead of thousands.

### 3.3 Pagination / filtering "without a server"

- **Pagination** is real and static: `/api/banks/page/<n>.json` with `meta.next/prev`.
  Page size is a build constant (50). RFC-style: `meta: {total, page, pages, page_size,
  next, prev}`.
- **Single-facet filtering** is real and static: fetch `/api/countries/de.json`,
  `/api/licenses/e-money-institution.json`, `/api/cards.json#visa`, etc.
- **Arbitrary multi-facet filtering** is client-side: load `/api/search-index.json` once
  (slim, ~40–60 KB gzipped), filter/rank in memory. The MCP server does exactly this so
  agents never see the mechanics.

### 3.4 Search endpoint

`/api/search-index.json` = one slim record per bank **plus** a lowercased `haystack`
string (name + hq + country + audience + note, truncated) and the `features_summary`
array. This is the static analogue of the homepage `/?q=` substring search (UX audit
§3). There is no server to run a query against, so "search" ships as a **downloadable
index + a documented client algorithm** (substring over `haystack`, optional facet
filters, rank exact-name > name-prefix > haystack). The MCP `search_banks` tool and the
existing homepage search both implement the same algorithm — one vocabulary, two
runtimes (mirrors the site's existing "JS `FIELDS` for interactive, static table for
SEO" pattern).

### 3.5 CORS & caching (vercel.json)

Extend the existing `headers` block (which already CORS-enables `data.json`,
`openapi.json`, `jobs/data.json`):

```jsonc
{ "source": "/api/(.*)", "headers": [
    { "key": "Access-Control-Allow-Origin", "value": "*" },
    { "key": "Cache-Control", "value": "public, max-age=3600, stale-while-revalidate=86400" }
] }
```

Add `/api/index.json` and `/openapi.json` to the homepage `Link:` header set and to
`.well-known/api-catalog` (both generated by `build-agents.mjs`) so the API is
discoverable via RFC 9727. Flow 31 asserts vercel.json keeps its security headers and
immutable app.js cache — additive changes here don't touch those.

## 4. Data requirements — Schema V2 fields used, and the one NEW field

### 4.1 Schema V2 fields consumed (no new fields needed for these)

The API/MCP is mostly a **serializer** over existing v1 + Schema V2 keys:

- Slim filters: `category`, `custody`, `regulation_type`, `region`, `countries`, `kyc`,
  `stablecoins`, and v2 `card_networks[]`, `card_form[]`, `card_funding[]`,
  `features.*` (all 19: `apple_pay`, `google_pay`, `api`, `webhooks`, `oauth`,
  `sandbox`, `business_accounts`, `virtual_cards`, `physical_cards`, `iban`,
  `self_custody`, `mpc`, `yield_bearing`, `savings`, `lending`, `investing`, `treasury`,
  `crypto`, `stablecoin_native`), `stablecoin_tickers[]`.
- Full record: everything, including v2 `payment_rails[]`, `timeline[]`, `partners{}`,
  `fx_markup_pct`, `cashback_pct`, `yield_pct`.
- `compare_banks` / `similar_banks` rank on `features.*` (tri-state → Jaccard over
  `true` keys) + `category`/`custody`/`region`/`card_networks` overlap.

**Tri-state invariant is load-bearing.** Every API/MCP consumer MUST honor the universal
rule: `null`/absent = *unverified*, never `false`. Slim `features_summary` lists only
`true` keys; it must not imply the omitted ones are `false`. `search_banks` filtering on
a feature returns only `true` matches and reports an `unverified_count` alongside
`total` so agents don't present "no match" as "confirmed absent" (mirrors SCHEMA-V2 UI
rule "facets show N unverified"). This is documented in the tool schema descriptions.

### 4.2 NEW field to flag — stable entity `id` / `slug`

**Problem:** `data.json` entities have **no persistent primary key**. Slugs are computed
at build time (`CMPSLUG` in app.js, `slugify()` uniquified in a `Map` in
`build-pages.mjs`). An API needs a stable, collision-free `id` for `/api/banks/<slug>.json`,
for `get_bank`, and so consumers can store references. Re-deriving the slug in a third
place risks drift (two banks named similarly could get renumbered).

**Recommendation (small, additive):** persist a `slug` (and optionally numeric `id`)
onto each entity as part of Schema V2 phase 1 — OR, cheaper, have `build-agents.mjs`
import the **same** `slugify`/uniquify routine `build-pages.mjs` uses (extract it to a
shared `tests/slug.mjs` module) so `/n/<slug>/` and `/api/banks/<slug>.json` are
guaranteed identical by construction. Preferred: shared module now, persist `slug` into
`data.json` when Schema V2 lands. **This is the only genuinely new data requirement.**

No other new fields are needed — the API surfaces what Schema V2 already defines.

## 5. Pipeline integration — exact seams

1. **`tests/build-agents.mjs`** (pipeline audit "machine-readable agent surface"): add an
   `/api/*` emitter next to the existing `openapi.json` / `api-catalog` /
   `agent-skills` writers. It already loads `data.json`, `changelog.json`, computes
   tallies, and writes JSON with a stable serializer. Add: slim mapper, sorted list,
   page shards, per-entity full files, facet shards, search index, `/api/index.json`.
   Reuse `CL.generated` for `as_of`. Runs inside `build-pages.mjs` → inside the
   reproducibility chain automatically.
2. **Extract `slugify`/uniquify** from `build-pages.mjs` into `tests/slug.mjs`; import in
   both builders (§4.2).
3. **`openapi.json`**: extend the generated spec with the new `/api/*` paths (still
   generated from the dataset so the field list can't drift — the existing design goal).
   Add the `features`/`partners`/etc. v2 properties to the entity schema when v2 lands.
4. **`vercel.json`**: add the `/api/(.*)` CORS+cache header block (§3.5).
5. **`.well-known/api-catalog`** + homepage `Link:` header: add `/api/index.json`
   (`rel="service"`), regenerated by `build-agents.mjs`.
6. **`/data/` dictionary**: flow 39 requires every `data.json` field to be documented on
   `/data/`. If §4.2 persists `slug` into `data.json`, add its FIELDS row (same
   requirement Schema V2 already carries for its new keys).
7. **Human landing page `/api/` (HTML)**: a single generated `/api/index.html` doc page
   describing the endpoints, in the standard sub-page shell (see §6). This is the only
   new *HTML* page and it goes through the normal generator block + `urls[]` + sitemap +
   footer-link registration (pipeline audit §2b seam).
8. **`sync-counts.mjs`**: if the `/api/` HTML doc states "368 banks / N endpoints",
   anchor those digits in `RULES` so flow 30 stays green.

The `/api/*.json` files themselves are **not** HTML pages, so the HTML-oriented flows
(canonical, breadcrumb, ≤160-char description, unique title) don't apply to them — but
they must be deterministic and committed for the reproducibility job.

## 7. MCP server

### 7.1 Where it lives

A **separate small npm package** in the repo at `/mcp/` (workspace dir, published as
`@neobankbeat/mcp`), so it versions with the data project but ships independently.
Layout:

```
mcp/
  package.json        # bin: neobankbeat-mcp; deps: @modelcontextprotocol/sdk, undici
  src/index.ts        # stdio server, tool registration
  src/data.ts         # fetch + cache of the static API
  src/tools/*.ts      # search_banks, compare_banks, similar_banks, get_bank
  README.md
```

Runs over **stdio**, launched via `npx @neobankbeat/mcp` — the standard local-MCP
distribution. (A hosted *remote* MCP would need request-time compute; static hosting
can't provide it, so remote is explicitly out of scope. The stdio package is the whole
shipment.) Config snippet users paste:

```jsonc
{ "mcpServers": { "neobankbeat": { "command": "npx", "args": ["-y", "@neobankbeat/mcp"] } } }
```

### 7.2 Tools & schemas

All inputs are JSON-schema-validated; all outputs return slim records by default (with
`get_bank` returning full). Every tool result includes `as_of` and the MIT citation
string, and — where a feature filter is applied — `unverified_count`.

- **`search_banks`** — filter + rank.
  Input: `{ query?: string, category?: enum, custody?: enum, region?: string,
  country?: string, regulation_type?: string, card_network?: string,
  features?: string[]  // AND over features.* true, kyc?: enum, stablecoins?: boolean,
  limit?: int=20, offset?: int=0 }`.
  Output: `{ total, unverified_count, as_of, results: SlimBank[] }`. Same algorithm as
  `/api/search-index.json` (§3.4).
- **`get_bank`** — `{ slug: string }` (or `name`) → the **full** entity object + `url`.
- **`compare_banks`** — `{ slugs: string[]  // 2–4 }` → a transposed comparison matrix
  using the same field vocabulary as the site's `VS_FIELDS` / homepage `FIELDS`
  compare table (UX audit §5): category, audience, hq, founded, custody, regulation,
  card_networks, cashback/`cashback_pct`, yield/`yield_pct`, fx_markup/`fx_markup_pct`,
  features diff, stablecoins/tickers, kyc, regions. Tri-state rendered as
  `true|false|null`, never collapsed. Includes the deep-link to `/vs/<a>-vs-<b>/` when
  that static page exists.
- **`similar_banks`** — `{ slug: string, limit?: int=5 }` → nearest neighbours ranked
  by Jaccard over `features.*` `true` keys + category/custody/region/card_networks
  overlap. Deep-links to `/n/<slug>/alternatives/`.

Tool descriptions restate the two house rules verbatim: (1) cashback/yield/fx are "up
to" figures — never present as guaranteed; (2) `null` = unverified, never false.

### 7.3 Staying in sync with the static data

**The MCP server fetches the static API at runtime — it bundles no data snapshot.** On
first tool call it `GET`s `https://www.neobankbeat.com/api/search-index.json` (slim, for
search/compare/similar) and lazily `GET`s `/api/banks/<slug>.json` for `get_bank`.
Responses are cached in memory keyed on the `as_of`/ETag; a `stale-while-revalidate`
refresh (default 1 h) picks up dataset changes automatically. Because the CDN already
sets `Cache-Control` on `/api/*` (§3.5), the server piggybacks on HTTP caching.

Result: **zero manual sync**. The dataset changes → `build-agents.mjs` regenerates
`/api/*` on the next build/cron → the MCP server sees new data within the cache TTL. No
version pinning, no vendored copy to drift. A pinned-snapshot fallback (embed the last
`search-index.json` for offline use) is optional and clearly labelled with its `as_of`.

The MCP package is registered in `.well-known/agent-skills/index.json` alongside the
existing skill (a second entry, `type:"mcp"`, generated by `build-agents.mjs`) and
listed in `/api/` docs + llms.txt, so agents discover it the same way they discover the
skill today. Its sha/version reference is generated, not hand-kept (same rot-prevention
rationale as build-agents already applies to the skill sha256).

## 10. Dependencies

- **Schema V2 (soft).** The API ships useful on v1 (`services[]`, `card_network`,
  `custody`), but `search_banks`/`similar_banks`/the feature matrix are only compelling
  once `features.*`, `card_networks[]`, `stablecoin_tickers[]` are populated (Schema V2
  phases 2–3). Design against the exact v2 key names now; degrade gracefully on v1.
- **One new data requirement:** a stable entity `slug`/`id` (§4.2) — a shared
  `slug.mjs` unblocks it immediately; persisting `slug` into `data.json` is the clean
  long-term form and rides Schema V2's additive phase-1 migration.
- Build seam: `tests/build-agents.mjs`, `tests/build-pages.mjs`, `tests/footer.mjs`,
  `tests/sync-counts.mjs`, `vercel.json`, `/data/` dictionary.
- External: `@modelcontextprotocol/sdk` (MCP package only; not in the site build).

## 11. Top risks

1. **Static hosting can't do arbitrary server-side queries** (biggest). The "REST API
   with pagination/filtering" is honestly *pre-generated shards + client/MCP-side
   filtering*, not a query engine. If consumers expect `?country=DE&feature=apple_pay`
   to return filtered JSON, they'll be disappointed. Mitigation: single-facet shards +
   a slim search index + the MCP server absorbing the query mechanics; document the
   model plainly; never imply arbitrary filtering. Do **not** reach for serverless
   functions — they break reproducibility and the "no server" design.
2. **Facet-shard explosion.** Multi-dimension shards would balloon the committed build
   and churn diffs. Mitigation: single-dimension shards only; cross-product is
   client-side (§3.2). Keep an eye on file count in the reproducibility diff.
3. **Tri-state leakage.** Slim `features_summary` and feature filters can be misread as
   "confirmed absent". Mitigation: only emit `true` keys, always return
   `unverified_count`, restate the rule in every tool/endpoint description. A regression
   here misinforms agents — treat as correctness, not cosmetics.
4. **Slug drift** between `/n/<slug>/` and `/api/banks/<slug>.json`. Mitigation: single
   shared `slug.mjs`; a flow assertion that every `/api/banks/<slug>.json` has a matching
   `/n/<slug>/` (extends flow 28's "href resolves" spirit).
5. **MCP data freshness vs offline.** Runtime fetch keeps it in sync but needs network;
   an embedded snapshot drifts. Mitigation: fetch-first with HTTP caching, optional
   clearly-dated offline snapshot, surface `as_of` in every response.
6. **npm supply-chain / maintenance surface.** A published package is a new attack/upkeep
   surface. Mitigation: minimal deps (sdk + undici), pinned, `npx -y` usage, generated
   version references so they can't rot.
